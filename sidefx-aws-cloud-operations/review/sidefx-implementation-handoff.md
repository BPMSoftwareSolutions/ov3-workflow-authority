# SideFX implementation handoff — no new execution authority

- Read the live SideFX server-side estate and exact provider identities before authoring/mapping. The operator's desktop environment is not evidence of available server capabilities.
- Reuse canonical `sfx`/SDA execution and the current server-side interface; do not add a special AWS harness, an AWS service registry that duplicates existing provider authority, or AWS-specific hand-authored consumer execution bodies.
- This package proposes public terminal circuits only. A root incident circuit can compose the narrower circuits through existing declared graph invocation/dependency mechanics; its outcome contracts must be compatible and its routing explicit.
- AWS supplier names are candidate physical services, NOT authoritative `@provider` capability IDs. `@provider` tags are intentionally absent. Add them ONLY after exact selected provider-capability IDs and operation bindings are known, then re-pin feature bytes.
- An AWS platform port is not an AWS provider capability. A fixture source is not a runtime provider. Keep scoped authorization and approval separate from running a built-in SSM document.
- Apply any needed feature/DSL/author path through existing installed mechanisms. Some versions of supplied compiler examples mark feature-pinning or provider-binding grammar as `not-built`; verify the current installed state before using that desired grammar.
- After authoring, retain feature bytes by sha256, declare selected identity/steps/contracts/event authority/outcome variants and operation, bind selected feature version, then call live feature conformance check. A local package validator is NOT `CONFORMANT`.
- For each case: create isolated state; invoke its *own exact request*; pin selected graph, provider binding, call/attempt, returned outcome, AWS readbacks and output digest. `$.status` alone is not evidence. No successful case can borrow another case's run.
- AWS effect tests require non-production sandbox accounts, scoped roles, purpose-built resources, explicit user approval, predictable rollback and cost controls. The accompanying synthetic arrangements never invoke real cloud resources.
- If real IAM or billing access is absent, perform a **clearly labeled simulation** and present the source-specific proof obligation. Do not describe fixture results as live AWS or SideFX telemetry.
- For operational security, no AWS keys or secrets in feature JSON, screenshots, demo state, Git, or flight recording. Use workload identities/vault-controlled access, redact and review testimony before public presentation.
