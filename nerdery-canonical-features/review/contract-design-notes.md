# Request, result and fixture interpretation

**Status: contract design notes, not installed JSON Schemas.** Exact IDs and observable values are in the `.feature` files. `derived/capability-index.json` is a projection for navigation, not a competing schema authority. Before declaration, create complete input and outcome contracts in the estate using its existing contract authoring surface and the accepted feature decisions. This pack does not claim schema conformance or an executable declaration.

## Shared proposed result convention

Each public operation returns exactly one terminal result. `status` selects one of the variants in its feature. A refusal includes `reason.code` with the exact case-specific diagnostic. Write results expose `mutation.applied`; successful outputs represent committed domain state, not a promise to commit later. Read refusals omit the relevant successful payload (`animal`, `items`, `team` or `presentation`); an absent unrelated field does not prove isolation. Input-validation errors must be deliberately mapped to these named outcomes by the declared admission/execution path; a generic transport error cannot silently stand in for a promised refusal.

The authenticated owner comes from the trusted execution context. It is absent from the request JSON. A fixture's subject is not a business input. Create-result identifiers that are not pinned by a case may be generated by existing mechanics; do not introduce a new allocation service just for these examples.

## Primary request families

| Capability family | Proposed request members | Required observable result |
|---|---|---|
| Registration / sign-in | `identityResponseRef` | Validated user profile or established session, or a named refusal |
| Section access | `section` | Allowed section or refusal, based on externally managed roles |
| Add definition | `animal` | Committed definition with common/scientific name, avatar, public number, county range, types, stats and optional attribute associations |
| Update/remove definition | `definitionId`, `expectedRevision`, and `animal` for replacement | Updated/removed state or unchanged-state refusal |
| Attribute changes | `attribute` or `attributeId`, `expectedRevision` | Reusable attribute definition with selectable values, or its removal disposition |
| Catalog browse | `search` | Collection-number-ordered active definitions, user-relative collected state and permitted animal properties |
| Definition detail | `definitionId` | The same lock boundary on direct reads, with shared attribute meaning when unlocked |
| Photo upload | `fileName`, `mediaType`, `contentBase64` | Owned durable photo reference and actual content digest; no species-verification claim |
| Record encounter | `encounterId`, `definitionId`, `location`, `photoRef`, optional `nickname` | One owner-scoped individual encounter and collection state |
| View collected / home | Empty request object | Owner-scoped individual records or selected-team presentation |
| Select team | `expectedRevision`, `encounterIds` | Atomic selected set of zero through six eligible individuals |
| Present page | `page`, `locale` | Localized presentation model preserving identities and permissions |
| Offline capture | `encounterId`, `definitionId`, `location`, `localPhotoRef`, optional `nickname` | Retained owner-scoped local draft explicitly pending synchronization |
| Offline synchronization | `encounterId` | One server-recorded encounter or a retained pending draft with its reason |

## Location

The two illustrated alternatives are manual `{source:"manual", description:...}` and device `{source:"device", latitude:..., longitude:...}`. These are proposed contract shapes. The source does not prescribe address fields, map picking, accuracy, validation ranges, observation timestamps or whether an encounter outside a definition's typical range must be rejected. Do not introduce those as requirements without a decision. Typical habitat range is not automatically a geofence.

## Collected state, individual state and team state

The catalog has one row per definition. `collectionState` reflects whether the current user has recorded that definition. The personal list retains one row per encounter identity. `displayName` uses the nickname when present and otherwise the common name; the photo remains the user's photo. Team members refer to encounter identities under proposed D06. No physical-animal deduplication or biometric identity is implied by the phrase individual animal.

The locked animal-property object has exactly `commonName`, `collectionNumber`, `range` and `avatarPhotoRef`. Envelope identifiers and collected-state metadata are not extra educational animal properties. Scientific names, types, stats and special-attribute mappings must not leak in alternative response branches, raw embedded state or cross-user caches.

## Important gaps that remain explicit

Photo storage metadata is not a verification workflow. Language fixtures are not a customer language decision. Passing projection-model tests is not proof of browser compatibility, responsiveness or accessibility. A source-generated workload fixture is not a load test. No actual DNR identity provider, state county catalog or complete production type catalog is fabricated by this package.
